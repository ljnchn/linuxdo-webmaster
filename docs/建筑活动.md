# 福利羊毛与资源荟萃：独立游戏内活动

## 范围与边界

用户要求移除「文档共建」建筑，并重构「福利羊毛」「资源荟萃」的建筑与内容。本文件说明这两栋建筑新增的独立活动规则与接口，不把初版平衡参数写成用户已确认的数值。

- 福利羊毛：「正经人谁花那个钱啊～ 此版块供羊毛、抽奖等福利使用。」
- 资源荟萃：「包括软件分享、开源仓库、视频课程、书籍等分享。」
- 所有清单、软件、仓库、课程、书目与徽章均为虚构游戏内容，不抓取或跳转真实优惠、软件、付费课程或外部抽奖网站。
- 「社区徽章抽奖」是游戏里的活动主题。15 星币是站长筹办活动的虚构游戏资源支出，不是玩家购买抽奖资格；没有真钱、真实奖品、概率收益或额外付费步骤。
- 活动与「富可敌国」赞助信箱完全独立，不发放赞助、赞助者身份或待领取赞助信封。
- 旧人物/世界事件定义、效果与日志不变；不改自动时钟、注册方式、邀请日名额、服务器、租期、维护费或赞助规则。

## 可调整的初版参数

每栋建筑至少需要 1 位佬友。每栋建筑任意一次活动成功后，该栋建筑所有选项共同等待 **7 个游戏日**，另一栋建筑不受影响。引擎日号达到「上次活动日 + 7」即可再开展，与现实时间、时段切换次数和自然周无关；后台/弹窗暂停时不会额外流逝。引擎日号从 0 开始，界面从第 1 天开始显示；冷却提示使用 `nextAvailableDay + 1`，与主界面一致。例如第 1 天开展后，第 8 天可再次开展，不改变实际 7 游戏日冷却。

| 建筑 | 活动 | 游戏星币成本 | 内容 | 氛围 | 尝试吸引佬友 |
| --- | --- | ---: | ---: | ---: | ---: |
| 福利羊毛 | 整理限免清单 | 0 | +2 | +3 | 0 |
| 福利羊毛 | 社区徽章抽奖 | 15 | 0 | +7 | 2 |
| 资源荟萃 | 软件分享 | 0 | +4 | 0 | 0 |
| 资源荟萃 | 开源仓库共读 | 10 | +7 | +1 | 0 |
| 资源荟萃 | 视频课程共学 | 15 | +6 | +3 | 0 |
| 资源荟萃 | 书籍共读 | 0 | +3 | +2 | 0 |

这六项数值和 7 日冷却都是当前可调试假设，不是用户给出的最终定值。每栋都有免费选项，没有强制付费解法。内容和氛围沿用 0–100 上限。

活动效果固定，不读取或推进游戏随机数 `rngState`。抽奖活动的入站人数由现有 `admit` 同一入口计算：关闭注册为 0；邀请注册共用当日最多 2 人名额；所有方式受服务器剩余容量约束。活动不会把新佬友变为富可敌国。即使预计入站 0 人，只要活动本身可开展，仍可选择支付 15 游戏星币获得固定氛围收益；界面可提前显示具体限制，完成日志再次说明实际入站人数与原因。

## 引擎接口

`src/engine.mjs` 导出：

- `BUILDING_ACTIVITIES`：冻结的六项定义，每项包含 `id`、`building`、`name`、`description`、`cost`、`rewards: {members, mood, content}`、`cooldownDays`。建筑键为 `benefits`、`resources`。
- `RULES.buildingActivityCooldownDays`：目前为 7。
- `activityStatus(state, building)`：只读状态查询，不修改存档、不耗 RNG。

`activityStatus` 返回：

```js
{
  building: 'benefits',
  cooldownDays: 7,
  lastUsedDay: null,       // 尚未使用为 null
  nextAvailableDay: null, // 尚未使用为 null；否则为上次活动日 + 7（从 0 开始的引擎日号）
  remainingDays: 0,
  canRun: true,           // 是否至少有一个可执行选项
  blockedReason: null,   // 整栋建筑的阻碍：结束、无人、冷却
  activities: [
    {
      // ...对应的 BUILDING_ACTIVITIES 定义
      canRun: true,
      blockedReason: null, // 也会检查此选项的游戏星币成本
      expectedMembers: 2,
      admissionReasons: [],
      admissionNote: '预计入站 2 位佬友。'
    }
  ]
}
```

`blockedReason` 中的「第 N 天」已转换为从 1 开始的显示日，界面可直接展示；`nextAvailableDay` 仍为从 0 开始的引擎日号。`expectedMembers` 仅预估当前注册/名额/容量条件下的入站人数，是否能执行仍以 `canRun` 为准。未拉新活动的 `expectedMembers` 为 0，`admissionReasons` 为空，`admissionNote` 为空字符串。拉新限制使用可读中文说明与稳定代码：

- `registration_closed`：当前关闭注册。
- `invite_quota`：今日邀请名额用完或只剩部分名额。
- `capacity`：服务器已满或仅剩部分空位。

在邀请注册且容量受限时可同时返回两项限制。关闭注册时只显示这一直接原因。UI 无需自行复制入站计算公式。

提交动作只能包含：

```js
{ type: 'activity', activityId: 'benefits-badge-draw' }
```

六个 ID：

- `benefits-free-list`
- `benefits-badge-draw`
- `resources-software`
- `resources-repository`
- `resources-course`
- `resources-book`

引擎和服务端均从可信定义读取成本与效果。引擎拒绝多余字段；`server/protocol.mjs` 的严格动作白名单同时拒绝未知 ID、缺失字段、客户端提供的成本/效果/建筑/日号。旧动作格式不变。

无人、结束、冷却或付费活动余额不足时直接拒绝，不消耗星币、不发奖励、不写账本、不加日志、不改变 revision。引擎先在副本上计算，并在返回前验证完整状态；服务端沿用现有原子提交、revision 比较和幂等键处理，不新增数据库结构。

## 存档、重开与备份

仍使用 v4 存档。新局不预写活动字段；在首次活动成功时增加可选账本：

```js
buildingActivities: {
  benefits: { activityId: 'benefits-badge-draw', day: 0 },
  resources: { activityId: 'resources-software', day: 3 }
}
```

账本只保存每栋最近一次活动，不存奖励快照或可由客户端指定的经济参数；成功开展下一次活动时覆盖该栋记录，另一栋记录保留。

- 字段缺失、`null` 或空对象均视为未活动，合法读取/迁移时原样保留，不替旧存档注入字段。
- 已有记录只能使用已知建筑键和所属活动 ID；日号必须是 0 至当前游戏日的整数；记录必须恰有 `activityId` 和 `day` 两个字段。
- 原 v4 存档继续有效；v3 迁移仍只沿用既有租期向上补齐规则，保留资产、进度、修订号和可选活动账本，不修改源对象。
- 确认重开后新局没有活动账本；本机备份、服务端前局备份与恢复均保存完整原始活动状态，恢复后冷却继续生效。
- 不变更存档键、备份键、历史操作响应、数据库迁移或赞助数据结构。

## 自动化验证

`tests/building-activities.test.mjs` 覆盖：

- 六项活动在经典/挑战模式的精确成本与奖励、状态不可变、RNG 不变、无额外赞助。
- 同栋所有选项共享冷却、另一栋独立、游戏日边界、满 7 游戏日可重做，以及冷却提示与主界面显示日一致。
- 精确余额、零币免费选项、内容/氛围上限，以及无人、结束、余额不足、重复点击的拒绝。
- 开放/邀请/关闭注册、邀请名额耗尽、部分/满容量、同时受限，预估与实际入站一致。
- 抽奖与旧欢迎事件共用邀请名额，旧事件效果不变。
- 缺失/null/空账本、v3/v4 兼容、恶意账本/奖励字段拒绝、重开清除、本机备份与恢复。
- 严格服务端输入、活动不推进时段、失败原子性、并发相同幂等键只执行一次、重启后重试保持一致、服务端备份保留账本。

运行：`node --test tests/building-activities.test.mjs`，以及项目 `npm run check`、`npm test`。活动测试不代表真实平台已接通，发布、平台配置与联网验收仍由原项目流程处理。
